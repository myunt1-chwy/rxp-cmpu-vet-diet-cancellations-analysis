#+TITLE: Database-derived cohorts instead of uploaded identifier payloads

* SQL contract
The eleven enrichment queries now derive their identifiers from Snowflake source
tables using named CTEs. Python supplies only validated scalar dates and, for
contacts, a timezone. It no longer serializes order IDs, line IDs, prescription
IDs, customer IDs, intervals, or SQL fragments into these queries. Warehouse
array expansion of actual upload-table columns remains legitimate and unchanged.

Each SQL file contains its entire cohort definition. The Jinja defaults document
the study dates; the rendered exports contain executable SQL with no Jinja.
Run =make cohort-sql-review= to materialize them locally, or
=make cohort-sql-check= to render and lint both templates and concrete SQL using
SQLFluff's default Snowflake rules. Neither command accesses the warehouse.
Shared-query exports are under =src/autogenerated/database-derived-cohorts/=;
the two target-owned queries export under their target's =src/autogenerated/=.

* Cohort definitions
- Contact queries: CMPU vet-diet CUSTOMER_UPLOAD first-order prescriptions in the creation window; aged cancellations with mature 7/14/21-day windows; same customer, product ID and unambiguous pet. Select the shortest-delay reorder per customer/horizon, then break ties by reorder timestamp, reorder order/line IDs and original order/line IDs. Deduplicate intervals and number them in order/time order. Preserve each query's handled/WISMO and strict-interval or all-history filters.
- Seven-day prescription and approval-channel enrichment: derive both original and reorder physical keys, or the reordered prescriptions, from eligible same-customer/product pairs. This earlier analysis does not require same-pet matching.
- Upload enrichment: require exactly one populated prescription on each side and different prescription IDs. Match warehouse upload entities by prescription and customer, preserving the upload cutoff and existing source audits.
- Selected upload/decision evidence: use the selected same-pet 7/14/21-day pairs, and derive prescription/customer/order/line keys from the database before joining upload and decision evidence.
- Auto-reorder flags: derive successful same-pet/part-number physical lines across mature 7 through 70-day windows. The all-aged population covers the union of the two first-order subsets; downstream cohort-specific denominators remain unchanged. Preserve missing ECOM matches and the existing customer-identity audit.
- Study financial lines: derive the prescription creation cohort and join all matching physical lines by prescription and customer, retaining the vet-diet line filter and shipment-level sales grain.
- No-recorded-cancellation statuses: derive the current study prescriptions and numeric first-order-item keys, match both first-order keys and customer, and require no populated cancellation reason across the matched shipment rows.

* Verification and limits
Compared the new CTE key selectors against retained warehouse extracts and the
historical extraction inputs, using local DuckDB only as an audit engine:
- Three contact queries: 5,986 distinct intervals each, with identical deterministic request IDs and timestamps.
- Seven-day prescription keys: 4,295 physical lines.
- Selected prescription keys: 11,907 physical lines.
- Seven-day upload requests: 2,139 prescription/customer pairs.
- Approval-channel requests: 2,143 prescriptions.
- Selected upload/decision requests: 5,978 prescription/customer/order/line keys.
- Auto-reorder lookup: 16,677 physical lines.
All compared key sets match exactly. Reviewed the two study-table CTEs against
their original source selection and retained downstream identity checks.
Cached contact, upload-evidence, auto-reorder and study-table workflows pass;
the report rebuilds without refreshing the warehouse.

The new queries read current warehouse state. In particular, current registry
membership and cancellation reasons need not reproduce the historical 40,864-Rx
no-cancellation cohort or the frozen financial comparison. Exact historical
re-extraction requires the original warehouse snapshot/history; it cannot be
recreated by injecting saved IDs. Existing cohort/identity checks still reject
mismatches before publication. A coordinated source refresh is required to
replace those report snapshots. No fresh warehouse execution was performed, so
current-warehouse result totals are not claimed to be verified.

* Retained snapshot replay
=shared/retained-query-snapshots.yaml= explicitly records eleven historical
query/Parquet fingerprint pairs. Cached builds may replay only those recorded
pairs (or an exact current-query match), verify the actual source bytes and all
existing cohort dependencies, and emit a warning distinguishing historical
replay from execution of the new SQL. Unknown query/data fingerprints still
fail. The recorded metadata is not relabeled as a fresh query result.
The auto-reorder cache normalizes migrated input paths while retaining exact
content hashes; all 36 input hashes are unchanged.

The source validator rejects reintroduction of templated JSON query inputs or
host-generated requested-key/upload-query fragments. The obsolete JSON-only
DuckDB template and lint-only requested_keys context were removed.
